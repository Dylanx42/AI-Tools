## 2026-09-15｜Delta

### 🔥 Session V3 / pre-step durable-write ordering｜⭐⭐⭐⭐⭐
- 新增一条与 9 月 12 日 `turn/end` hole 不同的 **现役 writer/read contract 不对称**证据：在 `0.1.5-rc.2` 中，`agent/pre-step` waterfall 发生在 `step/start` 与首个 V3 `system/message` protected surface head 写入之前；插件如果在 pre-step listener 里直接 `session.append('user/message', …)`，live writer 会接受，但 durable log 会把 surface message 写到 protected head 之前。
- 当前 master `c291e7961a` 的公开逐行复核确认 ordering 仍与 rc.2 一致；V3 strict/current validation 或 V2→V3 migration 会因 `system/message requires a protected first surface head` 拒绝这种日志。也就是说，**Harness 可以写出自己更严格读取路径不能接受的 Session 形态**。
- 官方文档/内置插件更安全的注入方式其实一直是 pre-step decision batch：`{ kind:'enter', messages:[...] }`，这些消息会在 system head 后持久化；但 V3 新增 protected-head invariant 后，过去第三方直接 append 的模式从“能工作”变成 durable compatibility trap。
- **为什么重要**：这进一步强化当前 Radar 的 Session V3 判断——问题不是单一 legacy migration bug，而是 writer-time invariant 与 reader/migration invariant 尚未完全对齐。所有 Context / Memory / instruction injection 插件都应把 **pre-step durable ordering + strict reopen** 加进 RC gate。
- **成熟度**：RC Runtime / Plugin contract 风险；默认继续观察官方是否在写入时拒绝 pre-head surface append，或提供更明确的 durable injection API。

### 🔥 Session V3 / legacy compaction span migration｜⭐⭐⭐⭐½
- 另有真实 `0.1.1-rc.2` 历史日志经官方 `v0 → v1 → v2 → v3` 链迁移时，旧 compaction/prune span 在 0.1.5 中不可寻址，迁移器会 fail-closed 拒绝整段 Session。
- **为什么重要**：历史 corpus gate 不能只覆盖 Subagent descriptor、permission preset、message source；还必须覆盖**做过 compaction/prune 的长期 Session**，否则最有价值的长会话反而更容易踩迁移边界。
- **成熟度**：RC migration 风险；继续观察 repair/migration closure。

### 👀 SessionHandle / write-claim lifecycle｜⭐⭐⭐⭐½
- rc.2 又出现长期 Web/Desktop 进程中的 write claim 生命周期问题：内核 lease 已不存在时，进程内 active write-handle claim 仍可能残留，导致某个 Session 持续报 `already owned by an active write handle`，直到整个进程重启。
- 当前公开复核认为不能简单用“内核对象不存在”判断 stale，因为合法的 created-but-unmaterialized Session 也可能没有内核对象；更合理的修复方向是让 claim 生命周期真正绑定 handle object。
- **判断**：这是 SessionHandle/cross-process lock 从“有锁”走向“生命周期正确”的实质验证点；暂不单独升 Candidate，纳入官方 DSH / Session P1。

### 趋势判断

官方最新仍是 **`0.1.5-rc.2`**，今天没有新 Release。真正的增量是 Session V3 的风险面再次扩大：除了旧日志 migration 和 steering 下的 `turn/end` hole，现在又确认了 **pre-step surface append 可被 writer 接受、却违反 V3 protected-head invariant**，以及长期 Session 的 compaction span / write-claim lifecycle 边界。

因此当前 0.1.5 RC 的 Session gate 应明确包含：**legacy corpus migration（含 Subagent / source / preset / compaction）→ durable injection ordering → 持续运行 writer integrity → strict cold reopen → write-handle lifecycle**。这比继续追新 UI 或 Star 变化重要得多。

## 2026-09-16｜Delta

### 🔥 官方 `0.1.6-alpha.1`：新开发线开启，但 integration correctness 风险集中暴露｜⭐⭐⭐⭐⭐
- 9 月 15–16 日公开复现已经明确使用 `@deepseek-ai/dsh@0.1.6-alpha.1`，因此 Radar 新增 **0.1.6 Alpha 开发观察线**；稳定候选基线仍保持 `0.1.5-rc.2`，两者不能混为同一兼容结论。
- 官方 computer-use 两个包在 `0.1.6-alpha.1` 缺少新 loader 要求的 `dsh.bundle` manifest；按官方 `dsh plugin add` 流程加入 profile 后会直接让 profile boot hard-fail。社区复核同时确认 `dsh-app-boot` 已严格要求 bundle patch，而已发布包元数据未同步，属于**官方包族内部 contract 不一致**，不是第三方插件噪声。
- browser-use runtime 还出现依赖层 scope identity 问题：重复物理 `dsh-scope` copy 会使第二个 Session 起无法解析 scoped context，说明 0.1.6 的 package/peer topology 本身也进入 compatibility gate。
- **判断变化**：0.1.6 Alpha 目前只作为前瞻观察线，不建议迁移；Compatibility gate 新增 `bundle manifest + physical dependency identity / peer topology`。

### 🔥 官方 Agent Teams × ACP persistence｜⭐⭐⭐⭐⭐
- `0.1.6-alpha.1` 官方 `dsh-experimental-agent-team-profile` 与官方 ACP + JSONL persistence 的最小对照中，**不挂 Agent Team patch 时 `session/new` / `session/prompt` 正常；挂载后在首个模型请求前即于 JSONL flush 阶段失败**。报告同时指出同类失败此前可在 `0.1.5-rc.1` 复现。
- 这是比“Agent Teams 有哪些控制能力”更重要的 correctness 证据：官方实验包与官方 surface/persistence 组合尚不能默认视为可互操作。
- **成熟度**：官方实验性维持不变；下一观察点上调为 ACP/Web/headless × JSONL 的跨 surface creation/resume matrix，而不仅是 waiting/Steer/cold recovery。

### 🔥 Compaction × reasoning-token accounting｜⭐⭐⭐⭐½
- 9 月 16 日新增报告：长会话 `/compact` 在 reasoning model 上可能因默认 `maxTokens=8192` 被 reasoning tokens 消耗而没有足够 summary output，导致 compaction 持续失败；现场复现来自旧 0.1.0 RC，但报告核对称相关默认在 `0.1.6-alpha.1` 仍未变化，适用于 DeepSeek V4 reasoning / GLM-5.3 一类模型。
- 这把 Compaction 风险从“旧 span migration”扩展到**当前模型 token accounting / summarizer budget contract**：即使 Session 结构本身合法，reasoning token 预算也可能让长期会话无法回收 Context。
- **判断**：进入 Session/Compaction P1 核心 gate；需要同模型 paired test，区分 reasoning budget、summary output reserve 与 provider usage accounting。

### 👀 MCP / Browser optional dependency fault isolation｜⭐⭐⭐⭐
- `0.1.6-alpha.1` 的 experimental Playwright MCP 若首次连接或 tools sync 失败，会中止整个 Agent activation；与浏览器无关的 Session 也无法 create/resume，Web UI 还会先发 `api-session/removed` 造成“会话消失”的假象，刷新后文件仍在。
- 这不是数据丢失，但属于 **optional capability failure → whole-session availability failure**。MCP Runtime 的观察标准因此从 cursor/deadline 继续扩展到 provider fault containment 与 UI error semantics。

### 趋势判断

今天最大的变化不是多了几个插件，而是 **0.1.6-alpha.1 已开启新的开发 cohort，同时官方自身的 package/profile/Agent-Team/MCP 组合暴露出明显 integration seam**。当前建议保持：生产/日常判断继续以 `0.1.5-rc.2` 为候选基线，0.1.6 Alpha 只做公开证据跟踪，不迁移、不安装。

后续优先盯三条：**0.1.6 package/bundle/peer topology 是否快速收口；官方 Agent Teams 在 ACP/Web/headless + JSONL 下能否完成 create→prompt→persist→cold resume；reasoning model 的 compaction budget 是否出现官方修复或 paired A/B 数据。**
