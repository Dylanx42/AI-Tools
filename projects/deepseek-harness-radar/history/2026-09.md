# DeepSeek Harness Radar｜2026-09 历史

> 当前状态 Dashboard：`../RADAR.md`。本文件只记录 2026-09 的每日增量。

## 2026-09-01｜Delta

### 👀 官方 DeepSeek Harness `0.1.2-alpha.3`｜P1
- 官方于 2026-08-31 发布 `dsh-v0.1.2-alpha.3`，观察窗口进入 alpha.3 cohort。
- 长会话分页导航和图片投递继续增强。
- **破坏性/迁移点**：移除可选 SQLite Session persistence backend；已有 SQLite 内容需要在旧版本中先导出。
- **判断**：0.1.2 的兼容窗口继续快速移动，alpha.2 的兼容结论不能自动外推到 alpha.3。

### 👀 Compatibility / Upgrade｜alpha.3 新迁移面
- 社区已出现基于 alpha.3 的真实迁移证据：旧 profile 需要重新核验 core bundle contract。
- 已有第三方插件迁移到 generated `ctx.remote` Client API，并移除已退休 runtime 依赖。
- **判断**：Upgrade Skill / compatibility matrix 需要继续覆盖 profile/core bundle、Client API 与 Session persistence。

### ⚠️ Runtime reliability｜alpha.3
- 有社区报告称任务回答后仍持续生成、不停止；目前尚未确认根因。
- **判断**：先作为 Runtime 风险跟踪。

### 趋势判断

9 月第一天的核心变量是 **官方 alpha.3 再次改变兼容基线**。优先验证 P0/P1 项目是否明确通过 alpha.3。

## 2026-09-02｜Delta

### 👀 官方 DeepSeek Harness `0.1.2-alpha.4`｜P1
- 当前官方兼容基线已推进到 `0.1.2-alpha.4`；社区梳理显示 alpha.1→alpha.4 的改动主要集中在 client、session、code-runtime、subagent 与 api。
- **新增迁移点**：alpha.4 将 Session 的事件序号和日志 offset 拆成不同类型；直接持有或透传 Session event、fork、compaction、subagent offset 的深耦合插件需要重新验证。
- 已出现 alpha.4 的 Session projection 持久化 schema 不匹配启动失败报告，Session/projection 升级仍是高风险区。
- **判断**：alpha.3 兼容标签不能自动外推，compatibility matrix 改以 alpha.4 为当前基线。

### 🔥 Subagent continuation / nested Agent contract｜P0 观察线
- alpha.4 continuation 存在 `running → waiting → settled` 三态，但 waiting 对父 Agent 不够可见，监督者仍可能需要主动查询状态。
- 嵌套委派中，manager 等待其子 Agent 后是否能被可靠唤醒并继续执行，仍存在明确 contract 缺口。
- **判断**：这直接影响 Agent Teams / Conductor 的多层委派、自治闭环与恢复正确性，加入 P0 下一观察点。

### 👀 Compatibility / Upgrade｜alpha.4 事实卡开始成型
- 社区已有 alpha.1→alpha.4 的系统迁移清单，也出现了部分插件早期 alpha 适配可直接延续到 alpha.4 的案例。
- 风险并非所有插件等比例增加，而是集中在深度耦合 session/api/runtime 内部结构的项目。
- **判断**：Compatibility 主线从“版本号兼容”升级为“依赖深度 + contract surface + real-host boot gate”的分层兼容模型。

### 🧪 dsh-provider-passport｜Candidate
- 新出现的 Provider 兼容预检插件，目标是处理 OpenAI-compatible 网关连通但真实 Harness 请求因 request dialect 差异失败的问题。
- 已提供 DSH `0.1.1-rc.2` 与 `0.1.2-alpha.4` 的完整预检、应用、真实 runtime 验证和回滚证据，并有 Windows/Ubuntu CI。
- **判断**：与企业网关 / 自建 Provider 场景高度相关，但仍是 preview，先放 Candidate，观察真实网关样本与误判/回滚边界。

### ⚠️ alpha.4 Runtime / Plugin ABI 风险
- 第三方 LLM adapter 若缺少后来新增的可选能力，可能影响 compact / auto-compaction，说明 adapter capability 的兼容保护仍需加强。
- 第三方 Host→Client 自定义事件仍缺少稳定的官方扩展 seam。
- **判断**：继续挂在 Runtime reliability / Plugin ABI，重点看 RC 前是否补 capability negotiation 与 extension seam。

### 趋势判断

今天的核心变化是 **alpha.4 把兼容问题进一步具体化为 Session event/offset、Subagent continuation、LLM adapter capability 和 Remote event seam 四类 contract**。0.1.2 已不适合只用“支持 alpha.x”这种单标签判断兼容，必须看插件实际耦合层级。

多 Agent 的关注点也开始从“有没有 Teams UI/调度器”进入 **嵌套 Agent 是否能可靠等待、被唤醒并继续执行** 的 Runtime 正确性阶段。

## 2026-09-03｜Delta

### 🔥 官方 DeepSeek Harness `0.1.2-rc.1`｜⭐⭐⭐⭐⭐
- 官方于 2026-09-03 发布 **0.1.2 系列首个 RC**，当前兼容基线正式从 alpha 阶段进入 `0.1.2-rc.1`。
- RC1 把前几轮 alpha 中最关键的底层变化正式固化：`Session.events` 改为按需读取 API `seq` / `eventAt()` / `snapshotEvents()`，`SessionSeq` 与 `SessionLogOffset` 强类型区分；SQLite Session backend 移除；Remote 网关统一调用 API，旧 APIProxy 已迁移并移除。
- 会话日志截断尾部现在会自动修复并明确告警；官方包也继续调整 peer dependency，目标之一是降低包管理解析和旧依赖混入的风险。
- **判断**：从今天开始所有 P0/P1 的兼容结论都以 **RC1 real-host 验证** 为准，不再以“支持某个 alpha”作为有效最终结论。
- **成熟度**：RC；继续观察，不把开发者预览等同于生产稳定。

### 🔥 Subagent Runtime｜双向 `send_message` 正式进入 RC｜⭐⭐⭐⭐⭐
- 父 Agent 与 continuable Subagent 现在可通过 **`send_message` 双向传递后续消息**，取代此前单向 `report` 的主要后续通信路径。
- 这直接对应过去几天一直跟踪的多 Agent continuation 问题：官方已经补上“通信通道”，但并不自动证明 **nested manager 等待孙 Agent、被可靠唤醒并继续执行** 的完整 continuation contract 已解决。
- **判断**：官方 Agent Teams / Subagent Runtime 继续保持 P0；下一步重点从“有没有双向通信”转向“等待、唤醒、有序性、cold resume 是否真正闭环”。
- **成熟度**：官方实验性 / RC Runtime；继续观察。

### 👀 Compatibility / Upgrade｜peer range 已不足以代表真实兼容｜⭐⭐⭐⭐⭐
- RC 前 alpha.5 已出现真实升级事故：从 `0.1.1-rc.2` 原地升级后，第三方 Profile 插件可把旧版 `dsh-session-projection-cache@0.1.0-rc.8` 带入新 Host，Host 随后调用新 `hydratePrepared` API，导致**所有旧 Session 都无法加载**。
- 同期还出现公开 API 缺口：`settingsNamespace`、`registerContinuableSetup`、`deepFreeze` 等第三方插件实际依赖的 surface 在最新主线不存在，包管理器却因宽 peer range 不报警，错误直到 Runtime load 才暴露。
- **判断**：Compatibility 模型再升级一层：除了版本号和 peer range，必须增加 **依赖树污染检测 + exact API surface + existing-session upgrade test + real-host boot gate**。
- **成熟度**：正在成型；继续观察官方 Upgrade Skill 与 RC1 实际插件矩阵。

### ⚠️ Session persistence / Runtime reliability｜RC 前暴露单写者边界
- alpha.5 还出现 JSONL Session ownership 仅在进程内生效的报告：两个 DSH 进程指向同一 persistence root 时，可能同时以 writer 身份恢复同一 Session，与“single-writer ownership” contract 不一致。
- 这类问题比普通 UI bug 更重要，因为它关系到多进程 / Desktop / Remote 场景下 Session 日志是否可能被并发写坏。
- **判断**：暂不单独升 Candidate；进入 RC1 Session persistence 可靠性重点验证项，等待 RC1 是否已修复或给出跨进程锁定 contract。

### 趋势判断

今天是 0.1.2 观察阶段的一个明显分界点：**问题不再是 alpha 每天改什么，而是这些 contract 能否在 RC1 上稳定下来。** 现在最关键的验证对象已经收敛为 Session/projection、Subagent continuation、Remote/Client API、Plugin ABI 与升级依赖树。

另一个重要变化是兼容判断标准彻底变了：**“peerDependencies 满足”只能说明包管理器愿意装，不能说明插件真的能跑。** 9 月接下来最有价值的证据会是 RC1 的真实启动、旧 Session 升级、长会话恢复和多 Agent 业务验收，而不是 README 自称支持。

## 2026-09-04｜Delta

### 👀 官方 DeepSeek Harness `0.1.2-rc.1`｜升级/打包一致性回归｜⭐⭐⭐⭐⭐
- Windows 用户在正常升级 RC1 后，官方内置 `@deepseek-ai/dsh-session-log-export` 可因依赖仍锁在旧 `0.0.1-rc.5` 而触发 client-modules `build-time externals drift`，直接阻止 Web 启动；单独把该包更新后恢复正常。
- 同日又出现历史会话加载报 `ctx.sessionQuery.observeSession is not a function` 的案例；当前源码中该方法仍存在，因此更像是**混合版本/部分升级导致 Runtime service shape 不一致**，而不是 API 被正式删除。
- **判断**：RC1 的“升级可靠性”风险明显上调。后续不能只做 clean install boot gate，还必须加入 **官方内置包版本一致性 + 原地升级后的 service-shape/历史 Session 验证**。
- **成熟度**：RC；继续观察，不建议把 RC1 当作无迁移风险版本。

### 👀 Provider / Models Runtime｜自定义 Provider 注册回归｜⭐⭐⭐⭐½
- RC1 有多份独立报告显示 `llm-pi-ai` settings namespace 在 Runtime 中可能没有成功注册：旧 `settings.yaml` 配置仍存在，但 Models 页面只剩内置 DeepSeek，自定义 Provider 消失，“添加 Provider”按钮也可能无响应。
- 这不是单纯 Provider API dialect 问题，而是 **settings registration / hot-upgrade Runtime 状态** 级别的故障，会直接让多 Provider 工作流不可用。
- **判断**：官方 DeepSeek Provider / 多 Provider 观察点增加 `settingsNamespace` 注册、升级后 catalog 恢复与保存失败可见性；等待官方确认根因。
- **成熟度**：RC 回归；继续观察。

### 🔥 Agent Teams × foreground one-shot Subagent｜Runtime 互操作缺口｜⭐⭐⭐⭐⭐
- 当 experimental Agent Teams profile 被挂载时，`workflow agent()`、`ralph` 和 `subagent(run_in_background:false)` 这类**前台一次性子 Agent**只要调用任意工具就可能整轮失败；纯文本成功，后台/continuable 子 Agent 不受影响。
- 公开复现把根因定位到创建时序：one-shot child 的 descriptor 在首个 pre-step 才落盘，但 `agent/created` 更早触发，Team roster 会短暂把它误判成 Team Lead；工具调用进入第二次 prompt assembly 后 membership 校验翻转为非成员并抛错。
- **判断**：Agent Teams 当前不仅要验证自己的 teammate 流程，还必须验证**与其他 Subagent 调度模式共存**。这直接影响 workflow/ralph/Conductor 组合使用，P0 保持但 Runtime interoperability 风险上调。
- **成熟度**：官方实验性；继续观察修复及回归测试。

### 👀 Subagent 成本可观察性｜usage 回传缺口｜⭐⭐⭐⭐
- RC1 的父 Agent 能拿到子 Agent 交付结果，但 `SubagentResult` 当前没有 usage 字段；token accounting 只落在子 Session 自己的事件流里。
- 对 Agent Teams / Conductor 来说，这意味着运行时无法直接做**任务级成本预算、路由或停止策略**，只能事后解析子 Session 日志。
- **判断**：先作为 Agent Runtime 治理缺口记录，不单独升 Candidate；观察是否进入官方 Subagent result contract。
- **成熟度**：机制缺口；继续观察。

### 趋势判断

RC1 发布后的第一天已经出现一个很明确的信号：**0.1.2 的风险正在从“API 还会不会改”转成“升级后不同包、服务和插件是否真的处在同一代 contract 上”。** 因此 RC 阶段最重要的 gate 应从 clean install 扩展到原地升级、官方内置包一致性、历史 Session、Provider settings 与混合插件组合。

多 Agent 方面也进入更细的 Runtime 正确性阶段：不仅要看 continuable Agent 能否双向通信，还要看 Agent Teams 是否会干扰 workflow/ralph/foreground one-shot 子 Agent，以及父 Agent 能否获得足够的成本/状态信息做治理。
