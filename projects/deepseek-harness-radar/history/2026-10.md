## 2026-10-01｜Delta

### 🔥 `0.2.0-rc.2` 继续作为主观察 RC；长期 compaction correctness 尚未闭环｜⭐⭐⭐⭐⭐
- 官方最新公开 Release 仍为 `dsh-v0.2.0-rc.2`（2026-09-29 发布），本日未发现更新的官方 RC/正式版。
- 9 月 30 日新增独立复现确认：此前 `0.1.7-rc.1/rc.2` 的 auto-compaction 到 context limit 不触发问题，在 `0.2.0-rc.2` 仍可复现。结合 9 月历史中 reasoning/output reserve、checkpoint non-convergence 等证据，说明 compaction 风险已经跨多个 release train 延续，不能仅以“0.2.0 已进入 RC”视为收口。
- **判断**：`0.2.0-rc.2` 保持主观察 RC，但仍不升为日常稳定基线。P0 继续要求 context-window progress invariant、触发阈值、summary output reserve、retry/backoff 与 strict cold-resume 的组合验证。

### 👀 Profile / Preset patchability 暴露新的配置控制面边界｜⭐⭐⭐⭐½
- 10 月 1 日新增公开报告指出：`$DSH_HOME/profiles/<name>/cordis.patch.yml` 只能稳定命中 top-level loader entry，无法直接 override agent preset 内部嵌套的可选 provider（示例为 preset 内 `tool-subagent-codex`）。这意味着 0.2.0 的 Profile-owned Settings / Agent Preset bundle 虽然把配置所有权进一步结构化，但用户级 patch 与 preset 内部 capability 的组合能力仍存在边界。
- 这不是单纯 UI 问题：如果可选 Subagent / Provider 已随 preset 分发但 profile patch 无法启用，Distribution/Profile 层就可能出现“能力存在、配置层却无法表达”的状态。
- **判断**：暂不把该问题外推成所有 nested preset 都不可配置，等待 maintainer 结论与最小复现；Compatibility gate 增加 **Profile patchability × nested preset capability** 检查。

### 👀 Desktop / Distribution：插件安装与 Session surface 继续暴露 RC 边界｜⭐⭐⭐⭐
- `0.2.0-rc.1` 官方 Desktop 上已有 dsh-TUI maintainer 报告：plugin-manager 会检查 bundle patch 中即使被 `disabled: true` 的旧 0.1.5-rc.3 package rows，导致 0.2.0 插件安装被错误拒绝并回滚。该证据来自真实插件维护者与官方 Desktop 环境，但当前仍需核验 rc.2 是否已修复。
- `0.2.0-rc.2` Windows Desktop 另有可重复报告：ACP/外部入口创建的 ungrouped sessions 在展开分组时可触发 renderer crash；Web/Desktop 也尚无直接查看/复制当前 session id 的入口。后者偏可观察性/UX，不单独改变成熟度；前者属于跨 surface Session projection correctness，继续纳入 Desktop 主线。
- **判断**：官方 Desktop 继续作为 P1 Runtime / Distribution 主线；第三方桌面壳只有存在官方未覆盖且可验证的差异化能力时才继续观察。

## 2026-10-03｜Delta

### 🔥 Session V3→V4 migration 出现 crash + silent downgrade incompatibility 组合风险｜⭐⭐⭐⭐⭐
- 10 月 2 日新增公开实测：Windows / Node 环境下，`0.2.0-rc.2` 对已有 Session store 执行 V3→V4 migration 时发生一次 SIGABRT（exit 134）。崩溃前约 157 个 `session.v4.jsonl.zstd` 已写入；报告者说明该 crash 当前仅观察到一次、尚不能稳定复现，因此不能把 SIGABRT 本身外推为普遍必现缺陷。
- 更强、且与迁移 crash 相互放大的证据是 downgrade 行为：迁移后切回固定的 `0.1.5-rc.3`，旧版本不包含 V3→V4 migrator / reader，Web sidebar 直接显示为空，而不是显式提示“store 已升级到 V4，需要新版本”。重新 pin 回 `0.2.0-rc.2` 后全部 Session 重新出现，说明该案例没有实际数据丢失，但形成了 **silent false negative / stranded corpus**：数据仍在磁盘上，旧 Runtime 却把不可读状态呈现成“没有 Session”。
- 这与 9 月持续观察的 legacy Session repair、writer integrity、cold reopen 属于同一 correctness 主线，但今天新增的是 **forward migration 后的 downgrade contract**。迁移是否原子、partial V4 写入后的 crash recovery、旧版本遇到 future-format 是否 fail loudly，都应成为正式 Compatibility gate，而不能只验证“新版能否读旧数据”。
- **判断**：`0.2.0-rc.2` 继续保持主观察 RC，不升为日常稳定基线。Session V4 风险从“legacy repair / migration correctness”进一步扩大为 **bidirectional version-boundary correctness**；升级前备份与明确版本 pin 仍有必要。等待 maintainer 对 SIGABRT 根因、migration atomicity 与 future-format detection 的结论。
