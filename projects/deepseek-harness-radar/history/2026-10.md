## 2026-10-01｜Delta

### 🔥 `0.2.0-rc.2` 继续作为主观察 RC；长期 compaction correctness 尚未闭环｜⭐⭐⭐⭐⭐
- 官方最新公开 Release 仍为 `dsh-v0.2.0-rc.2`（2026-09-29 发布），本日未发现更新的官方 RC/正式版。
- 9 月 30 日新增独立复现确认：此前 `0.1.7-rc.1/rc.2` 的 auto-compaction 到 context limit 不触发问题，在 `0.2.0-rc.2` 仍可复现。结合 9 月历史中 reasoning/output reserve、checkpoint non-convergence 等证据，说明 compaction 风险已经跨多个 release train 延续，不能仅以“0.2.0 已进入 RC”视为收口。
- **判断**：`0.2.0-rc.2` 保持主观察 RC，但仍不升为日常稳定基线。P0 继续要求 context-window progress invariant、触发阈值、summary output reserve、retry/backoff 与 strict cold-resume 的组合验证。

### 👀 Profile / Preset patchability 暴露新的配置控制面边界｜⭐⭐⭐⭐½
- 10 月 1 日新增公开报告指出：`$DSH_HOME/profiles/<name>/cordis.patch.yml` 只能稳定命中 top-level loader entry，无法直接 override agent preset 内部嵌套的可选 provider（示例为 preset 内 `tool-subagent-codex`）。这意味着 0.2.0 的 Profile-owned Settings / Agent Preset bundle 虽然把配置所有权进一步结构化，但用户级 patch 与 preset 内部 capability 的组合能力仍存在边界。
- 这不是单纯 UI 问题：如果可选 Subagent / Provider 已随 preset 分发但 profile patch 无法启用，Distribution/Profile 层就可能出现“能力存在、配置层却无法表达”的状态。
- **判断**：暂不把该问题外推成所有 nested preset 都不可配置，等待 maintainer 结论与最小复现；Compatibility gate 增加 **Profile patchability × nested preset capability** 检查。

### 👀 Desktop / Distribution：插件安装与 Session surface 继续暴露 RC 边界｜⭐⭐⭐⭐
- `0.2.0-rc.1` 官方 Desktop 上已有 dsh-TUI maintainer 报告：plugin-manager 会检查 bundle patch 中即使被 `disabled: true` 的旧 0.1.5-rc.3 package rows，导致 0.2.0 插件安装被错误拒绝并回滚。该证据来自真实插件维护者与官方 Desktop 环境，但当前仍需核验 rc.2 是否已修复。
- `0.2.0-rc.2` Windows Desktop 另有可重复报告：ACP/外部入口创建的 ungrouped sessions 在展开分组时可触发 renderer crash；Web/Desktop 也尚无直接查看/复制当前 session id 的入口。后者偏可观察性/UX，不单独改变成熟度；前者属于跨 surface Session projection correctness，继续纳入 Desktop 主线。
- **判断**：官方 Desktop 继续作为 P1 Runtime / Distribution 主线；第三方桌面壳只有存在官方未覆盖且可验证的差异化能力时才继续观察。

### 继续观察

- P1：Desktop Windows sandbox / renderer / installer；plugin-manager 对 disabled bundle rows 的兼容判断；Profile patchability；Provider / Codex / Claude / MCP 与 0.2.0 exact-pairing。
- Anchored / Scaffold 本日无新的 paired A/B、benchmark 或独立复现，不改变历史基线判断。

## 2026-10-03｜Delta

### 🔥 Session V3→V4 migration 出现 crash + silent downgrade incompatibility 组合风险｜⭐⭐⭐⭐⭐
- 10 月 2 日新增公开实测：Windows / Node 环境下，`0.2.0-rc.2` 对已有 Session store 执行 V3→V4 migration 时发生一次 SIGABRT（exit 134）。崩溃前约 157 个 `session.v4.jsonl.zstd` 已写入；报告者说明该 crash 当前仅观察到一次、尚不能稳定复现，因此不能把 SIGABRT 本身外推为普遍必现缺陷。
- 更强、且与迁移 crash 相互放大的证据是 downgrade 行为：迁移后切回固定的 `0.1.5-rc.3`，旧版本不包含 V3→V4 migrator / reader，Web sidebar 直接显示为空，而不是显式提示“store 已升级到 V4，需要新版本”。重新 pin 回 `0.2.0-rc.2` 后全部 Session 重新出现，说明该案例没有实际数据丢失，但形成了 **silent false negative / stranded corpus**：数据仍在磁盘上，旧 Runtime 却把不可读状态呈现成“没有 Session”。
- 这与 9 月持续观察的 legacy Session repair、writer integrity、cold reopen 属于同一 correctness 主线，但今天新增的是 **forward migration 后的 downgrade contract**。迁移是否原子、partial V4 写入后的 crash recovery、旧版本遇到 future-format 是否 fail loudly，都应成为正式 Compatibility gate，而不能只验证“新版能否读旧数据”。
- **判断**：`0.2.0-rc.2` 继续保持主观察 RC，不升为日常稳定基线。Session V4 风险从“legacy repair / migration correctness”进一步扩大为 **bidirectional version-boundary correctness**；升级前备份与明确版本 pin 仍有必要。等待 maintainer 对 SIGABRT 根因、migration atomicity 与 future-format detection 的结论。

### 👀 本日其他主线
- 官方 Release 页面未发现比 `0.2.0-rc.2` 更新的正式主线证据；Anchored / Scaffold、Agent Teams、Provider/Router、MCP/Skills 与 Desktop 未发现足以单独改变当前成熟度判断的新证据。
- 继续观察：V3→V4 crash-safe migration / downgrade fail-loudly；auto-compaction progress invariant；Subagent ownership / settlement；Desktop Windows sandbox；Profile nested preset patchability。

## 2026-10-04｜Delta

### 🔥 `0.2.0-rc.2` 出现“writer 自己写出 reader 拒绝读取”的 V4 Session correctness 新证据｜⭐⭐⭐⭐⭐
- 10 月 4 日官方 GitHub Q&A 新增公开报告：`0.2.0-rc.2` 的 tool-result pruner 在生成 replacement tool/result 时，可把替换记录追加到任何 open turn 之外；随后同一 Runtime 的 V4 reader 会拒绝该 Session。与 10 月 3 日记录的“旧 Runtime 不认识 future-format”不同，这次是 **同一版本内部 writer/reader invariant 不一致**，因此优先级更高。
- 这类故障不能只归类为显式可恢复错误：如果当前 turn 正常执行并持久化，之后 cold reopen / projection 才发现日志结构非法，用户看到的是“先成功写入、后无法读取”的 durable-state correctness 问题。需要继续核验触发 pruner 的阈值、replacement 记录的 turn ownership、是否影响已有 corpus，以及修复是否包含 writer-side invariant assertion 与 repair path。
- **判断**：Session V4 主线进一步从 migration / downgrade compatibility 扩大为 **writer → durable journal → reader 的端到端 invariant**。`0.2.0-rc.2` 继续只作为主观察 RC，不升日常稳定基线；Compatibility gate 增加“prune/compact 后立即 strict cold reopen + reader validation”。

### 👀 Desktop `cordis` preset 的 Skill 分发在打包形态下出现结构性断点｜⭐⭐⭐⭐½
- 10 月 2 日以来的 macOS/Windows Desktop `0.2.0-rc.2` 报告进一步表明：`cordis` preset 的 filesystem skill provider 指向打包后的 `app.asar` 内目录；Host 对该路径的读取/发现失败时，不仅内置 filesystem skills 丢失，还可能使 model-facing skill catalog 整体消失。Office skill 仍可加载，说明不是 Skill registry 全局失效，而是 preset + filesystem provider + packaged path 的组合问题。
- 这比单个 UI/路径 Bug 更重要：官方 Desktop 已成为 Distribution/Runtime 主线后，同一个官方 preset 在 source/web 与 packaged Desktop 之间不能默认视为 capability-equivalent。后续兼容验证需要显式加入 **source tree vs packaged app.asar × preset capability inventory**，并要求坏 skill root 做 fault isolation，不能拖掉其他 user/project roots。
- **判断**：官方 Desktop 维持 P1 Runtime / Distribution 主线，但 `cordis` / Skills 在 rc.2 上继续按 RC 风险处理；暂不外推到 standard preset 或所有 Skill provider。

### 继续观察
- P0：V4 writer/reader invariant、tool-result prune/compact 后 strict cold reopen、V3→V4 crash-safe migration、auto-compaction progress、Subagent ownership/settlement。
- P1：Desktop packaged preset capability parity、`app.asar` filesystem provider、Windows sandbox/host crashes、Profile/Preset patchability、Provider/MCP exact-pairing。
- 官方公开 Release 暂未发现比 `0.2.0-rc.2` 更新的正式 RC；Anchored / Scaffold 本日仍无新的 paired A/B、benchmark 或独立复现，不改变历史基线判断。

## 2026-10-05｜Delta

### 🔥 官方前瞻线推进到 `0.2.1-alpha.1`：Claude Code Mods compatibility 成为新的生态兼容主线｜⭐⭐⭐⭐⭐
- 官方 Release 已确认 `dsh-v0.2.1-alpha.1` 于 10 月 3 日发布。其最重要变化是新增 **实验性 Claude Code Mods compatibility layer**；官方明确限定当前目标是验证 Claude Code Mods API 的能力“大致是 DSH plugin capability 的子集”，并非宣称完整、可生产使用的兼容层。因此这条证据属于官方机制/架构方向确认，不能等价成“Claude Code 插件可以直接搬到 DSH”。
- 同版新增「让 Agent 创建插件」入口、可选 Developer Tools bundle（raw session logs、chat group/body 双向定位、Host diagnostics）以及 `--public-url` reverse-proxy surface。对 Radar 的意义是：此前分散观察的 Claude Code/Codex 生态兼容、插件诊断、Web/Remote 三条 P1 线开始被官方 Runtime 直接吸收一部分能力。
- 该 Alpha 同时包含 breaking change：移除 runtime invariant plugins / `./invariant` exports，并拆分 composer `stats` extension entry；第三方扩展与自定义 Profile 不能仅凭“0.2.x”版本号推断兼容，仍需 exact-pairing。
- **判断**：`0.2.0-rc.2` 仍是主观察 RC；`0.2.1-alpha.1` 新增为前瞻开发线，不替代 RC。Compatibility 主线新增 **Claude Code Mods bridge capability matrix + event/UI/loading gaps + third-party exact-pairing**；若后续出现真实 Mod 跨 Runtime 复用与独立复现，再考虑提升生态兼容成熟度。

### 🔥 Profile 热更新暴露 running-session lifecycle correctness：配置变化可中途 dispose 全部 Session｜⭐⭐⭐⭐½
- 10 月 4 日新增 `0.2.0-rc.2` Windows Desktop 报告：运行中的 Session 存在时修改 `cordis.patch.yml`，可使所有 running sessions 在 turn 中途同时被 dispose；UI 中会突然消失，看起来像被删除，但 durable logs 仍在磁盘，重新打开单个 Session 后可恢复。因此当前证据更接近 **runtime lifecycle / projection false-negative**，不是已证实的数据删除。
- 这与 9 月记录的 Settings mutate silent-success / rollback，以及 10 月的 Profile nested patchability 属于同一配置控制面主线，但新增的是 **live configuration transaction 对 active Session ownership/lifecycle 的影响**。如果配置重载允许在运行中发生，就必须定义 drain/restart/abort 语义，而不能以 silent dispose 作为隐式结果。
- **判断**：Compatibility gate 增加 **Profile hot reload × active sessions × mid-turn durability/cold reopen**；继续核验 `0.2.1-alpha.1` 是否改变该行为、是否有 maintainer 结论，以及 Web/headless 是否同样受影响。

### 👀 其他增量
- `0.2.1-alpha.1` 官方还修复 Desktop 默认端口策略（改由 OS 分配，规避 Windows reserved-port 启动失败）、大 Session 列表读取调度、bundle dependency mapping 的启停残留等问题，说明 Desktop/Distribution 仍处于快速收口阶段。
