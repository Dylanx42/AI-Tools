# 2026-10-30：实际 Agent 调用与新会话恢复合成验收

## 目标与环境

正式 Skill `2026.10.28.1` 已发布并安装，但此前的独立进程脚本通过不能证明实际 Agent
会使用已有项目，也不能证明一个没有前文的新会话能继续操作。本轮验证这两个边界，
只使用合成图；真实机柜图、Windows 实机和 Excel/WPS 继续暂缓。

- 平台：本机 macOS / Apple Silicon，Python 3.11.9。
- 入口：已安装正式 Skill 的 `scripts/run.py`，每次使用 `python3 -S`；Core 和依赖均从包内加载。
- 包版本与来源：`2026.10.28.1` / `d545490ad5697c2ccc3a597d9edf31b1372293da`，完整性校验通过。
- 新会话：Codex Desktop，运行时记录 `0.165.0-alpha.1.2`、模型 `gpt-6-astra`。
- 会话隔离：通过创建独立聊天开始，未 fork 历史；记录显示单一初始用户消息，未继承首会话内容。
  交接只提供 Skill、同一 SQLite、工作副本、待提交计划与回执路径和自然语言操作要求，
  未提供预先保存的设备 ID/状态答案；新会话不得读取前一会话或验收 oracle。

这是明确指定 RackTool 技能及安装目录后的实际调用验收，不声称验证所有软件的自动发现机制，
也没有重启整个 Codex 应用。生成器仅用于创建初始合成 XLSX，没有执行整套自检脚本代替 Agent。

## 合成输入与操作

初始工作簿包含两个 12U 机柜：`Room-Z / A01` 为降序 U，`Room-A / B01` 为升序 U。
两个机柜分别在 9–10U 和 6–7U 放置同名 `SYNTHETIC-SERVER`，用于检验唯一定位和歧义。
输入原件保留，所有编辑只作用于工作副本；项目 SQLite、计划、辅助状态、备份和证据独立保存。

| 阶段 | 实际执行 | 结果 |
| --- | --- | --- |

## 独立复核

主验收会话在新会话完成后额外进行只读核对，30 项断言通过：

- 项目 ID 不变，device/rack/placement/mapping ID 集合保持；另一台设备及其位置保持。
- 新会话首次读取的 SQLite 与交接文件逐字节 Hash 一致，恢复后的状态匹配交接快照。
- 同一个数据库路径继续使用，数据库旁 conversation-key 与原待办计划 Hash 保持。
  提交时 `save_project` 采用临时数据库校验后 `os.replace`，因此 inode 改变是正常原子保存，
  不能用 inode 是否相同来判断是否重建了业务项目。
- 原始合成输入未变；预览、重复提交拒绝及占用拒绝没有改变工作副本和数据库。
- 除 Core 查询之外，使用标准库只读检查 XLSX XML：原位置文字已清除，目标为
  `SYNTHETIC-RECOVERED`、`D5:D7` 三行合并；另一设备保持在 `D9:D10`，两种 U 方向保持。
- 原版面导出的两个原机房 worksheet XML 与最终工作副本逐字节一致；两种导出都含两个机房及位置表。
- 实际命令指向安装包；记录中的 token 参数已脱敏。新会话日志也遮盖了 style_signature，
  逻辑状态比较排除此日志遮盖字段；相同 SQLite Hash 和主会话最终 Core 读回提供独立数据证据。

最终结果为 **PASS：macOS Codex 明确调用 Skill + 独立新会话从同一项目继续操作（合成数据）**。
本轮没有发现需要修改 Core 的问题，没有更改源码或已安装包，也不发布新版本。
本次 30 项结果核对与新会话 29 次 CLI 调用不是全套 pytest 数量，不与历史测试计数相加。
