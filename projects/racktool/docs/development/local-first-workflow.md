# RackTool 本地优先、云端协作开发规范

生效：2026-10-26（北京时间）。用户本地 Astra 可用期间，本地承担主开发；云端按明确任务协作。
本规范替代此前“云端开发、本地只验收”的分工。模型可用性变化时交接任务，代码和产品不绑定某个模型。
Skill + AI 对话 → RackCore/CLI 仍是使用路线，GUI 不恢复为当前开发重点。

## 分工与代码依据

| 位置 | 默认职责 |
| --- | --- |
| 本地 Agent（当前使用 Astra） | 需求细化、源码实现、调试、回归、实际 Agent 调用和 Excel/WPS 验收 |
| 云端 Agent | 受委派的代码审查、独立模块、复现、测试或文档；先取得对应分支和提交 |
| GitHub | 正式主线、任务分支、PR、CI、设计/修复记录和成品发布 |

正式代码以远端 main 为准；进行中的任务以指定分支和提交为准。本机未提交/未推送的内容也是
待保护的工作，云端看不到时不得假定不存在，更不能让旧云端副本覆盖它。
每个任务明确一个负责人，默认本地。云端不主动重复实现本地正在修改的同一功能或文件。
并行工作拆为独立分支/worktree，交接时说明文件范围和依赖，由负责人集成并复测。

## 第一次本地接管

让本地 Agent 先定位实际仓库并只读检查；用户不需要手动逐条执行：

```bash
git status --short --branch
git worktree list
git branch -vv
git log -5 --oneline
git diff --stat HEAD -- projects/racktool
```

接着 fetch 远端 main，核对当前分支的领先/落后、未推提交、未跟踪源码及其他工作区。
不能用历史路径、2026-10-08 的干净状态或云端状态代替本次本机检查。
不为同步而 reset、自动 stash、删除分支或覆盖原目录。未提交改动、私有样本、SQLite、计划、
数据库旁 conversation-key/applied 标记和备份先保留；交接摘要不输出密钥或业务内容。

新任务从最新 origin/main 建独立工作区；继续已有任务时，先保留并核对其实际分支和改动，
不从 main 重新实现一遍。仓库不存在时才克隆；无需复制旧 .venv、.git 或模型登录配置。

## 源码开发与发布包验收分开

**现在要开发源码，本地需要仓库 checkout。** 原先“只装完整 Skill 即可”的方式继续适用于日常使用
和成品验收。Release ZIP 中的 Core 固定在发布提交，修改仓库不会更新已安装 Skill。

开发时在选定工作区的 projects/racktool 内执行（Python 3.11+）：

```bash
python scripts/dev.py setup
# macOS/Linux：使用当前工作区自己的解释器
.venv/bin/python -c "import racktool; print(racktool.__file__)"
.venv/bin/python -m racktool --help
python scripts/dev.py check
```

Windows 对应解释器为 `.venv\Scripts\python.exe`。macOS 可用确认版本的 python3，Windows 可用
py -3.11 调用 dev.py。setup 是源码开发环境安装，不是安装成品 Skill 时临时构建发布包。
各工作区使用自己的 .venv，检查导入路径确实属于当前源码。开发调用项目解释器的 `-m racktool`，
Agent 可读取仓库内 SKILL.md 和命令文档；不默认调用全局旧 Skill 的 scripts/run.py 来验证新代码。
不直接修改已安装 Skill 的 core/vendor，也不同时加载两份同名 Skill 来猜实际使用哪一份。

普通 Core/CLI/Skill 开发不要求 Qt；涉及保留 GUI 的变更才使用 setup/check 的 --gui。
本机装有既有私有 Golden 时检查加 --require-private；缺少数据要记录跳过，不能记为真实图通过。
首次建立开发环境做完整基线；日常先跑受影响回归，代码交付按项目要求完成完整检查和相应 CI。
以前的测试数量与平台结论是历史证据，本次执行结果另行记录，不沿用为本次 PASS。

## 本地与云端如何交接

1. 本地完成一个可解释的阶段，将指定文件提交并 push 到任务分支，记录精确 commit 和 PR。
   没有完成也能交接明确标记为进行中的提交；只提交预期源码，不上传私有数据、密钥或运行状态。
2. 交给云端：任务目标、分支、提交、文件分工、当前问题、测试结果及下一步。云端先确认实际拉到
   该提交；未提交内容不会随聊天或 GitHub 自动同步。无法 push 时单独保留基础提交及源码补丁。
3. 同一任务换负责人时，原负责人停止写入并记录状态，接手方从已推送的进度继续。模型额度耗尽
   不等于任务自动交接；先完成这个检查点，避免本地和云端同时改同一分支。
4. 独立云端子任务用独立分支/PR；结果交回负责人整合。每次交接至少包含：

```text
任务 / 当前负责人 / 状态（进行中、已暂停、待审查）
分支 / 提交 / PR / 允许修改的文件
已完成 / 未完成 / 已知风险或阻塞
已跑检查、平台、源码或包路径 / 人工验收状态
下一步与接手方
```

5. 完成后更新修复记录与必要 ADR，通过代码检查和对应 CI，按授权 squash 合入 main、删除远端
   临时分支。本地保留私有数据，并在工作区状态核清后同步已合并代码；不盲目 pull 覆盖进行中工作。

main 更新不代表已安装 Skill 更新。需要成品时，由发布流程创建新版本和成品 ZIP，验证来源提交、
校验和及独立安装，再更新本地 Skill。不得覆盖旧 Release/移动旧标签；仅改变本开发分工不发布新包。
旧安装和业务目录分开备份；源码验收通过后，发布包还要做一次脱离仓库的实际调用检查。

## 下一轮本地优先事项

先验收已经实现的五项工作流，收集真实问题，再选择下一项功能：

- 实际 Agent：读取技能、唯一定位设备、查询空闲 U、预览/提交、重启后从同一 SQLite 继续。
- 陌生布局：inspect/propose/check，方向与数量人工核对，低置信/歧义不强制通过。
- 已有设备：在原图工作副本改高、改名、跨机房移动，核对稳定 ID、合并和 U 方向。
- 位置表回导：从当前 SQLite 新导出，Excel/WPS 实际保存后预览/提交；保留隐藏 ID/元数据，
  U 范围与高度一致。旧表缺元数据时重新导出，不能重新 import 来代替保留原项目身份。
- 失败保护和交付：占位、过期/token、重复执行须正确拒绝；核对原件 Hash、备份、原版面与标准导出。

源码测试、成品包测试、实际 Agent 调用、Excel/WPS 外观/保存各自记录；脚本通过不代替真机结果。
真实图、预览计划、SQLite、密钥和日志保持私有，不因本地/云端换负责人自动上传。
业务状态绑定源文件绝对路径与 Hash，直接复制 SQLite 不算完成跨电脑迁移，不手改 SQL 冒充重定位。

## 会话管理和本地接管提示词

保留一个“RackTool｜本地主开发”和一个“RackTool｜云端协作”入口即可；这是建议命名，不表示已经
创建或重命名会话。按功能开有边界的任务，重要状态写进仓库和交接摘要。归档前核清未推代码、
脏文件和私有备份；不随模型切换删除历史工作区。云端无法读取本机状态时如实说明。

把下面一段交给已接入 Astra 的本地 Agent：

> 请接管 RackTool 本地主开发，云端按分工协作。先读取 AI-Tools 根及 projects/racktool 的
> AGENTS.md、README 和 docs/development/local-first-workflow.md，检查本机所有相关工作区、
> 分支、未提交/未推代码及私有状态，保护现有成果后核对远端 main。不要 reset、自动 stash 或删除
> 旧工作区。新任务用独立分支，开发使用该工作区 .venv 的源码 Core，报告实际导入路径，避免测到
> 全局旧 Skill 包。先完成源码基线和已有五项流程的真实 Agent/Excel-WPS 副本验收，记录实测结果
> 与未完成项；当前没有授权另起 GUI 重写或无关新功能。阶段性 commit/push 并保留交接摘要，
> 需要云端协作时给出分支、提交和具体文件分工。模型配置和密钥留在本机，不写进仓库或输出。
