## 2026-09-14 V0.5 GUI usability addendum

`04d15f6` 基线后的 macOS 人工检查发现：原 Qt 窗口虽然满足 headless API 测试，但三组大表格、
原始 ID 暴露和单设备即时写回流程不符合“普通同事无需 CLI 即可工作”的 V0.5 产品验收。该结果
被判定为范围内缺陷，旧 GUI 没有被伪报为人工 PASS。

当前重构候选保留原 RackCore 与 Safe Sync，并新增单机柜可视化、友好设备详情、移动抽屉、
待同步队列、批量 WritePlan 和唯一的全局设备移动提交入口。GUI 不导入 `openpyxl`；设备列表最多
物化 100 行，机柜场景只渲染当前选中机柜，避免此前完整 710-by-8 控件树带来的可用性和
macOS Accessibility 风险。

后续五项操作者反馈补齐了异常处理入口、可拉伸且可排序的机柜列表、完整多行设备文字、中文异常
与重扫路径、设备筛选和按源 Sheet 行列位置绘制的总览。独立 macOS 视觉 QA 还发现并修复了
headless 断言漏掉的“可点击异常卡片收缩为空白条”问题，并加固分隔条命中范围、非 active 状态
中文化及同步意外异常的 fail-safe GUI 处理。

2026-09-15 又补齐了由 RackCore 负责的 Excel 标准导出：GUI 顶部可直接导出，文件内固定包含
“机柜图”和“设备位置表”两个 Sheet。机柜按源 Sheet/行/列排序，多行文字完整保留，设备位置表
带筛选；公式样式文字按普通文本保存。导出拒绝覆盖源工作簿，并经过临时写入、重载验证和原子替换。

当前独立验证为 full **142 passed / 0 skipped**、integration **83 passed**、private real-Golden
regression **3 passed**、Safe Sync **28 passed**、headless GUI **30 passed**，Ruff 与 strict mypy
均 PASS；CLI inspect/analyze/import/rescan/export smoke 通过。真实私有 Golden workbook 的临时副本完成
**90 racks / 710 devices** 加载、四页面视觉渲染以及两 Sheet 导出/重载/逐 Sheet 渲染。macOS
native window 已启动供用户验收，但
启动和技术负责人视觉复核都不等于用户完成人工作业验收，当前仍标记
**MANUAL VALIDATION PENDING**；Windows 与 Excel/WPS 实机验证也保持 pending。详细状态见
[V0.5 gate](V0.5.md)。

## 1. Integration provenance

本次工作不是用较新的分支机械覆盖 `main`：

- 审计任务记录将 `main` 中已有的 GPT-5.6 Sol 成果作为权威输入之一；这些实现与 monorepo
  中其他项目的提交均必须保留。
- `racktool/v0.5-local-gui` 带入 Grok 后续推进的 V0.2～V0.5 增量；它同样只是待验证输入，
  不能因版本号较新而自动胜出。
- 合并提交 `a915f3321bcde6230db62abdef7d616ecb803007` 先把当时最新 `main` 整合进审计分支，
  建立包含双方成果的工作状态。
- 后续根据 AGENTS、Requirements、Architecture、ADR、ROADMAP 和行为测试重新选择或整合实现，
  而不是采用机械的 `ours` / `theirs`。

主要审计修复依次包括 Reader/Profile 门禁加固、Identity/Safe Sync 不变量、Profile 项目生命周期、
包导入环、Excel 元数据保护、threaded comments 拒绝策略，以及需要相互佐证的设备身份匹配。

## 2. Key defects found and fixed

### V0.1 / V0.2

- Reader 与 Profile 的通用性、边界输入和 fail-closed 行为重新经过行为测试，避免用固定样本、
  固定列号或弱匹配替代通用规则。
- Profile 现进入 project import、SQLite 持久化和 rescan 生命周期；持久化副本会重新验证，缺失、
  损坏或伪造 Profile 会阻断操作而不会修改工作簿或项目状态。
- 消除了 Profile 与 Core 的包导入环，顶层包导入和 CLI 启动重新可验证。

### V0.3

- 早期身份匹配可能过度依赖单一 range、文本或样式证据，在交换、重名、删除后重现等场景中有
  误复用身份的风险。
- Rack 与 Device 现在采用多证据匹配；Device 的文本复用必须得到 source/range 或结构证据佐证。
  证据冲突、重复或不足时 rescan fail closed，调用者不会持久化被拒绝或部分变异的项目状态。
- 回归覆盖设备交换、改名并移动、机柜改名/迁移/移除后重现、歧义拒绝及 SQLite 重开。

### V0.4

- Safe Sync 补齐 source binding、SHA freshness、设备高度、边界/占用、Mapping 歧义、merge 冲突、
  多列设备宽度、临时写入重载校验及工作簿+SQLite 事务回滚。
- 空值单元格不再等价于“可安全覆盖”：action source/target 范围内的 comment、hyperlink、data
  validation 和静态 defined name 会在 plan/preflight 阶段阻断；范围外元数据有保存回归。
- 现代 threaded comments 会被 openpyxl 丢弃，因此 Safe Sync 在 openpyxl load/save 前只读检查
  XLSX package；发现 `xl/threadedComments/` 或相关 `xl/persons/` part 时明确拒绝。
- 写入失败、重载失败、数据库保存失败和备份恢复失败路径均保持源工作簿不被半写或静默损坏。

### V0.5

- CLI 与 `GuiSession` 通过同一个 RackCore 高层事务执行工作簿和 SQLite 更新，不直接调用
  openpyxl 写 Excel，也不会分别提交半完成状态。
- Headless GUI 覆盖打开项目、列表/Mapping/冲突、move plan、Safe Sync、导出和备份恢复。
- Excel 标准导出由 RackCore 创建独立文件；GUI 不导入 openpyxl。导出覆盖两个 Sheet、完整换行、
  源版面排序、筛选、公式注入保护、源文件拒绝和失败时旧导出保护。

## 4. Golden Sample evidence boundary

- 历史 V0.1 验收使用一个真实私有机柜工作簿，其中包含两类实质不同的 Sheet 布局；每类均有
  Sheet-scoped expected JSON、源文件 Hash 和持久验收记录。
- 资产清单工作簿只作为独立对账参考，**不是第二个机柜布局 Golden Sample**。
- 原验收记录中的 90 racks、710 device anchors 和 710 placements 是历史完整结构审计结果；
  本次审计只把 3 项 private regression 作为当前自动化证据，不伪装成重新执行了历史人工审计。
- 私有源文件、expected、分析结果和 acceptance 保留在 Git 忽略的 `samples/private/`；不得提交
  业务内容。Synthetic fixture 只证明通用行为，不能冒充真实 Golden。
